## 1. The technician profile never reaches the primary model — FIXED

**Where:** `api/app/extraction.py`, `_call_groq`.

`_call_groq` accepted `profile` and `caption` and used neither, while
`_call_gemini` injected both. The text chain's primary entry is
`groq:openai/gpt-oss-120b` (`config.py`, `extraction_text_chain`), so on the
normal path the nightly profile was built by `memory.py`, stored in
`persons.profile`, read by `/process`, passed all the way down into `_run_chain`
— and then silently dropped.

Net effect: the "fifth model" feature only did anything on the days Groq failed
over to Gemini. Nothing logged an error, and `refresh_profiles` still reported
`refreshed: N`, so it looked healthy from every angle.

**Fixed by:** inject `_profile_block(profile)` into the Groq system message, the same
way `_call_gemini` does. `caption` stays unused there on purpose — it only ever
arrives on the image path, and `_call_groq` rejects images two lines earlier
(no vision model in the free Groq catalogue).

**Regression test:** `api/tests/test_extraction_profile.py`.

## 2. Any API restart cancels that day's report — FIXED

**Where:** `api/app/jobs.py`, `_loop` and `_due`.

`_loop` seeded `last_run[name] = started` (process start) for every job except
`sheet_queue`. `_due` for `daily_report` / `weekly_report` gates on
`last.date() < now.date()`. So after a restart at 08:00, the 18:30 check
evaluated `today < today` → False → **the daily report never went out that day**.
Same for the weekly one on its chosen weekday. A `docker compose up -d --build`
in the morning silently cost the day's report.

The seed was there for a real reason — without it, a restart at 19:00 (after the
18:30 send) would see `last is None` and send a duplicate. So neither `None` nor
`started` is correct: the scheduler needs to know when the job **actually last
ran**, across processes.

**Fixed by:** `logs.last_job_runs()` reads the newest `job:<name>` row per job out of
`pipeline_logs` (which `_record` already writes to via `write_safe`), and `_loop`
seeds `last_run` from it. No new table — the run history was already durable, it
just was not being read back. Falls back to the old process-start seed when the
log store is unreachable, so a DB outage degrades to today's behaviour rather
than to duplicate mail.

**Regression test:** `api/tests/test_jobs_schedule.py`.

## 3. The scheduler can die, against its own stated rule — FIXED

**Where:** `api/app/jobs.py`, `run()` and `_loop`.

The module docstring states the invariant: *"A job never raises into the
scheduler."* It was enforced at the leaves (`_execute` catches everything) but
not at the supervisor:

- `run()` ended with `return result["status"]` — a bare `KeyError` if the worker
  thread ever died before writing that key.
- `_loop` called `run(name)` with no `try`/`except`, so anything escaping `run`
  killed the scheduler thread and with it **all six jobs**, silently, until
  someone noticed the Sheet had stopped filling.

**Fixed by:** `run()` uses `result.get("status")` and records a real failed run if it
is missing; `_loop` wraps each `run(name)` so one exploding job cannot take the
loop down. The classic supervisor bug — the invariant has to hold at the loop,
not just at the leaves.

**Regression test:** `api/tests/test_jobs_schedule.py`.

## Closed in the follow-up pass

### 4. Login timing oracle — FIXED

The `user is None` / `password_hash is None` branch returns **before** bcrypt
runs. A real account costs ~100 ms, an unknown address ~2 ms. That is exactly
the distinction the docstring promises not to make ("one indistinguishable
failure for 'no such account', 'wrong password' and 'account disabled'").

**Fixed by:** on the miss path, `verify_password(password, _dummy_hash())` runs and
its result is discarded, so every failure costs one bcrypt round. `_dummy_hash`
is `@lru_cache`d and hashes a random token, computed lazily so importing the
module still needs no bcrypt.

### 5. `_login_failures` grows forever — FIXED

`_login_allowed` prunes each key's timestamp list but never removes the key when
the list empties; only a *successful* login pops it. One dict entry per address
that ever failed a login, for the lifetime of the process.

**Fixed by:** `if not hits: _login_failures.pop(client, None)` instead of writing back
an empty list.

### 6. `read_reports()` returns its own cache by reference — FIXED

Returns the `_reports_cache` list object itself. Any caller that sorts, reverses
or pops in place corrupts the cache for every other caller until the 30 s TTL
expires. Nothing does today — this is a tripwire, not a live failure.

**Fixed by:** the cache hit returns `list(_reports_cache)`. The row dicts stay
shared — copying a few hundred references is cheap next to a 1 s Google call,
deep-copying every cell would not be.

### 7. Two Sheets API calls per write — FIXED

`update_report_fields`, `clear_row` and `append_report` each GET the header row
(`Rapports!1:1`) before writing. The header changes approximately never. On the
drain path this is one extra call **per parked row**.

**Fixed by:** `_headers(svc)`, a 300 s TTL cache cleared by the same
`invalidate_reports()` the writes already call, so a renamed column still lands
immediately. All three write paths go through it.

### 8. A DB write on every authenticated request — FIXED

`UPDATE persons SET last_seen_at = now()` runs on every request that carries a
session cookie. The dashboard polls several panels on an interval, so this is a
write per poll per panel, permanently. Auth is on the read path of everything,
so anything it writes becomes amplification proportional to the poll rate.

**Fixed by:** only update when the stored `last_seen_at` is older than ~60 s
(`WHERE last_seen_at < now() - interval '60 seconds'`).

### 9. `send_daily_report` / `send_weekly_report` ~95% duplicated — FIXED

~50 duplicated lines: manager bucketing, director recipients, the per-manager
loop, `save_manager_report`. The only real differences are the row filter and
the period label.

**Fixed by:** one `_period_report(label, rows, kind)` called by both; each caller
keeps only its own row filter and its own period key (`date` vs `period`).

### 10. The dashboard polls while the tab is hidden — FIXED

`window.setInterval` does not check `document.visibilityState`, so a backgrounded
tab keeps calling the API — and burning Google Sheets quota — all night.

**Fixed by:** the interval checks `document.visibilityState` before fetching, and a
`visibilitychange` listener fires one immediate refresh on the way back, so the
first thing the user sees is current rather than however stale the tab got.

Related, lower priority: two components mounting the same `key` each run their
own fetch and their own interval, so the module-level cache dedupes the *paint*
but not the *request*.

### 11. Unbounded `limit` query params — FIXED

`/history`, `/media` and `/logs` take `limit: int` with no ceiling, so a client
can ask for everything in one call.

**Fixed by:** `Query(default, ge=1, le=...)` on all seven — `/history`, `/media`,
`/messages`, `/logs`, `/sheet-queue`, `/notifications` and `/n8n/executions`.

## Notes that are not findings

- `mailer.send` puts every recipient in one `To:` header, so managers see each
  other's addresses. Fine inside one company; would need BCC if it ever reached
  people outside it.
- `daily_report.py` calls `settings.gemini_model` / `groq_llm_model` directly
  instead of using a `provider:model` chain like `extraction.py` and `memory.py`.
  It works, but it is the one generator that cannot be re-ranked from `.env`.
- `sheets.read_reports` has a small thundering-herd window: two threads missing
  the cache at once both call Google. Harmless at this scale.
